# Milestone 0.1: Project setup

## What was built

- **An npm workspaces monorepo** with four packages, each named `@epochs/<name>`:
  - `shared`: the clocks from CLAUDE.md as constants (`TICK_MS` 250, `SUBTICKS_PER_TICK` 10, `SUBTICK_MS` 25, `MACRO_TICK_MS` 60 000) and `REGION_SIZE_TILES` (64). Nothing else yet.
  - `server`: a plain `node:http` listener on port 8787 with a `/health` endpoint. Milestone 0.2 attaches the WebSocket connection and tick loop to it.
  - `client`: Vite serving a blank dark page. It logs `Epochs client (tick 250 ms)` to the browser console, which proves it can read from `shared`.
  - `tools`: one helper that locates `content/`. The content checker comes in 0.3.
- **Folders:** `content/` and `docs/reports/`, kept in git with `.gitkeep` files.
- **TypeScript:** strict mode, one shared base (`tsconfig.base.json`). Each package extends it and adds only its environment.
  - The base also turns on `noUncheckedIndexedAccess`, so looking up a tile in an array gives `T | undefined`. That will catch off-grid lookups in 0.2.
- **Purity guard on `shared`:** it is type-checked with no Node types and no DOM. `process`, `setTimeout`, `window`, `fs` and the like fail to compile there, which enforces rule 2. I checked this by adding a file that used all three and watching it fail.
  - This doesn't catch `Math.random` or `Date.now`, which are part of plain JavaScript. A lint rule or test for those could come later if we want it.
- **Vitest:** a single root configuration, with each package as its own project. Twelve small tests: the clock constants, the server's health check, the client and tools importing from `shared`, and the workspace-link repair (below).
- **Root scripts:** `npm run dev`, `npm test`, `npm run test:watch`, `npm run typecheck`, `npm run check-links`. The CLAUDE.md commands section is filled in.
- **Workspace-link check** (`packages/tools/src/workspace-links.ts`). It runs automatically before `dev`, `test`, `test:watch` and `typecheck`, and makes the repository safe to move. See "After moving the repo" below.
- **`.gitignore`** for Node and Vite.

**Dependencies added (all dev-only, at the root):**

| Package | Version | What it's for |
| --- | --- | --- |
| typescript | 7.0.2 | Type checking |
| vite | 8.3.8 | Client dev server and build |

## How to run it

Needs Node 22 or later. The project was built on 22.21.

```
npm ci           # once after cloning: installs exactly the versions in package-lock.json
npm run dev        # client: http://localhost:5173   server: http://localhost:8787/health
npm test
npm run typecheck
```

## What to check by hand

1. Run `npm run dev`. You should see the server's line `Epochs world server listening on http://localhost:8787 (tick 250 ms)` and Vite's `Local: http://localhost:5173/`.
2. Open http://localhost:5173. It should show a blank dark page titled "Epochs".
3. Open the browser console. It should show `Epochs client (tick 250 ms)`.
4. Open http://localhost:8787/health. It should show `{"ok":true,"tickMs":250}`.
5. Stop it with Ctrl+C and confirm both processes are gone, using the steps in "Checking that Ctrl+C stops everything" below.

## After moving the repo

npm links each workspace package (`@epochs/shared` and the rest) into `node_modules`. On Windows those links are *junctions*, which can only store absolute paths. When the repo moved from OneDrive to `C:\epochs`, they kept pointing at the old OneDrive folder, so the server and client failed with `ERR_MODULE_NOT_FOUND` for `@epochs/shared`. `package-lock.json` was never the problem, because it records the links as relative paths.

- **Fixed now:** `node_modules` was rebuilt with `npm ci`. `package-lock.json` is byte-for-byte unchanged, so every version is exactly as locked.
- **Fixed for next time:** a small check runs before `npm run dev`, `npm test`, `npm run test:watch` and `npm run typecheck`. If a workspace link points anywhere other than this repo's `packages/` folder, it re-points the link and prints `Repaired workspace link ...`. It removes only the link, never the folder it pointed to. If `node_modules` is missing or a package was never installed, it stops and says to run `npm ci`. You can run it on its own with `npm run check-links`.
- **Fresh clone:** `npm ci` creates correct links. Nothing else is needed.
- **Tested:** I copied the repo with its links still pointing to `C:\epochs`, and `npm test` in the copy repaired them and passed. Then I moved that copy so its links dangled. `npm run dev` there repaired them, started both processes, and `/health` answered. The links in `C:\epochs` itself were untouched.

## Checking that Ctrl+C stops everything

I tested this with a script that starts `npm run dev` in its own console window and sends it a real Ctrl+C, the same signal a keypress sends. It ran 26 times: in PowerShell and cmd.exe, both after start-up and while Vite was still starting. Every time, both ports were free and no project `node.exe` was left within a few seconds. `concurrently` stays as it was, and nothing in `package-lock.json` changed.

To check by hand, in PowerShell:

1. `cd C:\epochs`, then `npm run dev`. Wait for `Epochs world server listening on http://localhost:8787` and Vite's `Local: http://localhost:5173/`.
2. Press **Ctrl+C** once. In PowerShell the prompt comes back. In cmd.exe you may be asked `Terminate batch job (Y/N)?`. The processes are already gone by then, and either answer is fine. Run steps 3 and 4 in a second PowerShell window *before* answering, to prove it.
3. Check the ports. This should print nothing:
   ```
   Get-NetTCPConnection -LocalPort 5173,8787 -State Listen -ErrorAction SilentlyContinue
   ```
4. Check for leftover processes. This should print nothing:
   ```
   Get-CimInstance Win32_Process -Filter "Name='node.exe'" | Where-Object { $_.CommandLine -like '*C:\epochs\*' } | Select-Object ProcessId, CommandLine
   ```
5. Run `npm run dev` again right away. It should start with no "port in use" error. Press Ctrl+C to finish.

**What is not covered:** killing the parent process from outside the terminal, for example ending `npm`'s `node.exe` in Task Manager or stopping it from a tool. That skips Ctrl+C entirely, and Vite and the server keep running, holding ports 5173 and 8787. Vite is set to fail rather than move to another port, so this shows up right away as "port in use" on the next `npm run dev`. To clear it, end the processes from step 4:

```
Get-CimInstance Win32_Process -Filter "Name='node.exe'" | Where-Object { $_.CommandLine -like '*C:\epochs\*' } | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```
